### Мета

Навчитись практично реалізовувати типові задачі DevOps рівня Junior+/Middle з **AWS базового+ рівня**, **Git**, **CI/CD** та **Terraform** на прикладі простого, але “реального” деплою **елементарної веб-сторінка**, яка **автоматично оновлюється після пушу в Git**.

---

## 1) Сценарій

Потрібно розгорнути в AWS мінімальну інфраструктуру та застосунок:

- **Публічний доступ по HTTPS** через **ALB**
- Інстанси застосунку в **приватних сабнетах**
- База даних **RDS** в приватних сабнетах (без публічного доступу)
- Домен в **Route53**, сертифікат **ACM**
- Вся інфраструктура — **Terraform**
- Деплой змін — через **CI/CD pipeline** (автоматично з Git)

---

## 2) Функціональні вимоги до застосунку (мінімум)

Застосунок може бути **будь-який простий** (наприклад, Nginx зі статикою, Node.js/Flask “Hello”, тощо), але має виконувати 2 умови:

1. Віддавати веб-сторінку:
    - `GET /` повертає HTML з текстом типу: `Hello from <env> - version <git_sha>`
2. Використовувати **RDS** хоч мінімально:
    - або зчитати з БД рядок “message” і показати на сторінці
    - або мати endpoint `GET /health` який перевіряє підключення до БД (і повертає 200/500)

> Важливо: RDS має бути реально підключений (не “заглушка”).
>

## 3) AWS вимоги (що саме очікується)

### Networking

- **VPC** з мінімум 2 AZ
- **Public subnets**: лише для ALB/NAT (за необхідності)
- **Private subnets**: для EC2 та RDS
- (Опційно) NAT Gateway для виходу в інтернет з приватних сабнетів (або альтернативний підхід і пояснення в README)

### Compute + LB

- **ALB** в public subnets
- Таргет(и): **EC2** (можна ASG, можна 1 інстанс — але пояснити вибір)
- **Security Groups**:
    - ALB SG: allow 443 from 0.0.0.0/0
    - App SG: allow inbound тільки від ALB SG (потрібний порт)
    - RDS SG: allow inbound тільки від App SG (порт БД)

### TLS + DNS

- **ACM certificate** (DNS validation)
- **Route53 record** (наприклад `devops-test.<your-domain>`), який веде на ALB
- Веб доступний тільки по **HTTPS** (HTTP → redirect)

### Database

- **RDS** (Postgres або MySQL)
- **Publicly accessible = false**
- Пароль/секрети **не хардкодити** в репозиторій

## 4) Terraform вимоги

- Вся інфраструктура створюється через Terraform
- Структура репозиторію має бути читабельною (мінімум):
    - `infra/` (Terraform)
    - `app/` (код сторінки/сервісу)
- Очікується:
    - `variables.tf`, `outputs.tf`, `providers.tf`, `main.tf` (або аналогічно)
    - адекватні `outputs` (ALB DNS, домен, важливі ресурси)
- **State management**:
    - S3 backend + lock
- Рекомендовано:
    - Передбачити універсаотеість терраформ темплейтів щоб можна було деплоїти ним різні середовища (environments dev/prod)

## 5) Git вимоги

- Репозиторій в Git (GitHub або GitLab — на вибір)
- Має бути нормальна (чиста) історія комітів принаймні в main бренчі
- Рекомендовано:
    - хоча б feature branch + PR/MR в `main`
    - захист від прямого пушу в main
    - вибрати Branching Strategy
    - придумати за яких умов буде деплоїтися application

## 6) CI/CD вимоги (обов’язково)

Пайплайн має робити наступне **автоматично**:

### На кожен PR/MR

- `terraform fmt` / `terraform validate`
- `terraform plan` (без apply)
- (опційно) lint/тести застосунку

### На merge в main

- `terraform apply` (або apply тільки інфри, якщо застосунок деплоїться окремо)
- деплой застосунку так, щоб **зміни веб-сторінки з main автоматично з’являлися на сайті**

### Як саме деплоїти застосунок — на твій вибір, але очікується автоматизація

Приклади прийнятних підходів:

- user_data на EC2 тягне артефакт (zip/tar) з S3, який CI/CD оновлює
- CI/CD будує AMI (packer) і робить rolling update ASG
- CI/CD робить SSH/SSM deploy на інстанс(и) (не ідеально, але допустимо якщо аргументовано)

## 9) Критерії перевірки підходу

- Розділення public/private subnet, коректні SG
- RDS приватний, не світиться назовні
- HTTPS через ALB + ACM
- Terraform readable, повторюваний apply
- CI/CD реально деплоїть зміни з Git
- Remote state + locking
- Немає секретів у репо
- CloudWatch logs/metrics, мінімальна observability
- Автоматичне “zero-downtime” оновлення (rolling)
- SG без “0.0.0.0/0” (окрім виходу в інтернет, там де треба)
- Автоматичний деплой без pipeline
- Відсутність Хардкод паролів/ключів
